# Roadmap — تحويل «رِحلتي مع القرآن» إلى منصة متعددة المستخدمين

> حالة العمل (2026-11-07): الأساس وOTP وتدفق Google OAuth مع PKCE موجودة في `feature/multiuser-auth-foundation`. Google provider مفعّل، وPreview ينجح في بدء التفويض إلى Google؛ ما زال اختبار حساب حقيقي وcallback والجلسة وعزل المستخدمين مطلوبًا. التسجيل العام لا يُفتح قبل استكمال إعداد البريد والأمان.

## سجل التدقيق والتقدم

- راجعنا PR #16 وتغييرات فرعه، ثم شغّلنا `npm test` (94 اختبارًا ناجحًا) و`npm run build:pages` بنجاح قبل تعديلات هذا الفرع.
- فحصنا تسجيل الدخول، OTP، استعادة كلمة المرور، الكوكيز، حماية Origin، RLS، التخزين المتفائل، استيراد الضيف، والبوابة المعطلة افتراضيًا.
- أصلحنا تأكيد كلمة المرور قبل التسجيل وعزل بيانات الضيف أثناء إعداد أول حساب، مع إعادة الضيف بأمان عند إغلاق الإعداد.
- جعلنا إثبات استعادة كلمة المرور أحادي الاستخدام: يُستهلك صف nonce مرتبط بالمستخدم عبر حذف ذري محمي بـRLS قبل تغيير كلمة المرور.
- بيانات المشروع متاحة وقد تأكدت صحة المشروع والجداول؛ لا تتوفر صناديق بريد اختبار مصرّح بها ولا يمكن إثبات التسليم أو مزامنة جهازين/عزل حسابين على خدمة حية.
- قبل هذا التغيير كانت الاختبارات 98؛ أصبحت `npm test` تشمل الآن 108 اختبارات. بناء Pages ينجح، لكن تحقق Auth والبريد على خدمة حية يظل معلقًا.
- أضيفت قوالب عربية RTL لتأكيد البريد والاستعادة، وواجهة/API لطلب إعادة OTP مع عدّاد انتظار 60 ثانية ورسائل لا تكشف وجود الحساب.
- فُحص Cloudflare Pages عبر الاتصال: المشروع لديه `rihlati-quran.pages.dev` فقط ولا توجد نطاقات مخصصة. تعذّر ضبط SMTP أو Resend عبر الاتصالات المتاحة؛ ولم يُرسل بريد حي.
- أضيف تدفق Google Authorization Code مع PKCE عبر Supabase Auth وPages Functions، و`state`/verifier في cookie مؤقت موقّع وHttpOnly. القيمة الافتراضية للعلم `false`؛ Preview وحده مضبوط على `true`. اختبار بدء حي عاد بتحويل Google وcookie محمية، دون إتمام دخول أو إنشاء حساب.

## القرارات التقنية

- **الواجهة:** المحافظة على HTML/CSS/JavaScript الحالية، مع الحفاظ على المصحف والتسميع وورد اليوم والخطة المرنة والـRTL والخطوط.
- **الاستضافة:** Cloudflare Pages؛ API في Pages Functions. لا نعرض مفاتيح حساب Supabase للمتصفح.
- **الهوية:** Supabase Auth (بريد + كلمة مرور قوية، تحقق بريد برمز OTP، تسجيل الدخول والخروج، نسيت كلمة المرور). الجلسة في Secure + HttpOnly + SameSite=Lax cookies؛ التحقق من Origin قبل الكتابة.
- **التخزين:** جدول `public.user_state` في Supabase Postgres، مفتاحه الأساسي `user_id` مع RLS لكل صف، وبداخله الحالة الحالية بصيغة JSONB (MVP)، رقم `revision` للمزامنة المتفائلة، تاريخ تحديث.
- **حماية المستخدمين:** لا نستخدم `service_role` لقراءة بيانات المستخدم؛ نستعمل JWT المستخدم مع سياسات RLS. كل API يثبت الهوية ويرفض كتابة صف مستخدم آخر.
- **الخصوصية:** لا تُرفع سجلات المتصفح إلى أي حساب تلقائيًا. الضيف يظل متاحًا في المرحلة الانتقالية، وتختفي بيانات الحساب من الواجهة بعد تسجيل الخروج.
- **البيانات الحالية:** تخزين المتصفح `rihlati-quran-v1` لا يتغير ولا يُمسح. عند الربط أول مرة يختار المستخدم: خطة جديدة من الصفر أو نقل نسخة محلية بعد تأكيد صريح. أي تعارض أثناء المزامنة لا يُكتب فوقه بالقوة.
- **المستخدم الجديد:** لا تُنسخ له الجلسات والبيانات الأولية الخاصة بمؤلف الموقع؛ يبدأ بسجلات فارغة وخطته يحددها بنفسه.
- **لا AI:** لا يعود المساعد الذكي أو مفاتيحه أو خدماته.

## مخاطر الإطلاق — مطلوب من مالك المشروع

1. إنشاء/وصل مشروع Supabase وتوفير `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY` في Cloudflare Pages على **الخادم**. لا تستخدم `service_role`.
2. تشغيل SQL من `supabase/migrations/001_user_state.sql` في مشروع Supabase، ثم التحقق من RLS بحسابين فعليين.
3. إبقاء Email confirmation إلزاميًا. طبّق قوالب `supabase/templates/confirm-signup.html` و`supabase/templates/reset-password.html` في لوحة Email Templates؛ كلاهما يستخدم OTP ويذكر صلاحية 10 دقائق، لذلك طابق مدة Auth معها.
4. اختر نطاق إرسال يملكه المشروع وأكمل DNS verification في Resend، ثم أعد SMTP المخصص قبل جمهور حقيقي؛ البريد الافتراضي في Supabase محدود حاليًا إلى رسالتين/ساعة وعناوين فريق المشروع. إعداد Turnstile وحدود Auth أساسي لمنع الإساءة. الخطوات في `docs/SUPABASE_SETUP.md`.
5. إعداد سياسات الخصوصية والشروط ووسيلة دعم/حذف حساب ونسخ احتياطي. **لا ندّعي أن النظام جاهز إنتاجيًا قبل اختبار كل ما سبق**.
6. `GOOGLE_SIGNIN_ENABLED=true` يظل افتراضيًا `false`. حاليًا مضبوط في Preview بعد نجاح بدء التفويض؛ لا تفعّله في Production قبل اختبار دخول حقيقي وحسابين وعزل البيانات.
7. `ACCOUNT_REGISTRATION_ENABLED=true` يُسمح فقط بعد اكتمال الإعداد الأمني والبريد. في غيابه تظل المنصة الحالية تعمل كضيف بلا تعطل.

## تكامل البريد الحالي

- Supabase Auth يظل مزود الهوية الوحيد؛ لا يوجد backend إرسال بريد منفصل ولا Resend SDK.
- Pages Function يدعم إعادة إرسال تأكيد التسجيل عبر `/auth/v1/resend` وإعادة طلب الاستعادة عبر `/auth/v1/recover`. واجهة التحقق تعرض عدّاد 60 ثانية، فيما تبقى حدود Auth/SMTP هي الحماية من الطلبات المباشرة خارج الواجهة.
- استعادة كلمة المرور وطلب إعادة التأكيد للحسابات الحالية يبقيان متاحين حتى عندما يكون التسجيل العام معطلًا؛ لا يفتح ذلك إنشاء حساب جديد.
- استجابة الاستعادة وإعادة الإرسال موحدة للحساب المعروف/غير المعروف ولحالات المزود/الحدود، ولا تدّعي التسليم إلى Inbox. المطلوب فحص Resend Logs ووصول البريدين الاختباريين.
- ملفات HTML آمنة للقوالب: `supabase/templates/confirm-signup.html` و`supabase/templates/reset-password.html`. عناوين الرسائل ومدة OTP وخطوات النشر في `docs/SUPABASE_SETUP.md`.
- مانع حالي: Pages لديه فقط `rihlati-quran.pages.dev` دون custom domain. لا يمكن توثيق أو مصادقة هذا النطاق المملوك لـPages لإرسال البريد؛ يلزم نطاق يملكه المشروع مع DNS. تظل إعدادات البريد والخطوات التابعة لها معلقة.
- مفاتيح SMTP/Resend لا تحفظ في GitHub أو ملفات المستودع. Supabase SMTP password هو Resend API key ويُدخل في واجهة أسرار Auth فقط.

## تكامل Google OAuth

- Google OAuth يستخدم مزود Supabase Auth نفسه، دون Resend أو SMTP أو OTP بالبريد. Pages Function يبدأ Authorization Code مع PKCE ويستعمل `/auth/v1/token?grant_type=pkce` لتبادل الكود من الخادم.
- Cookie `__Host-rihlati-oauth-flow` قصيرة العمر وموقّعة و`Secure; HttpOnly; SameSite=Lax` وتحمل `state` وverifier. callback يقارن state، يرفض أكواد الخطأ أو المعاد استخدامها، ثم يضع جلسة Supabase في كوكيز الجلسة الموجودة. لا يظهر session token في URL أو JavaScript أو `localStorage`.
- زر **الخروج والدخول بحساب آخر** ينهي جلسة Supabase، يعيد وضع الضيف المحلي، ويفتح شاشة الدخول. طلب Google يضم `prompt=select_account` لإظهار مبدّل حسابات Google؛ إذا كانت تغييرات المستخدم غير مؤكدة، يلزم تصدير نسخة احتياطية قبل التبديل.
- Supabase يتحقق من حالة OAuth مع Google. التطبيق يتحقق أيضًا من `state` المربوط بالـcookie ويرفض أي وجهة callback خارج مساره الثابت. النطاقات المطلوبة فقط `openid email profile`.
- زر Google لا يعمل إلا إذا كان `GOOGLE_SIGNIN_ENABLED=true` وأكد Supabase المزود من `/auth/v1/settings` أو من تحويل endpoint التفويض إلى Google للـcallback الدقيق. القيمة الافتراضية للعلم مغلقة؛ التسجيل بالبريد له علم مستقل ويظل مغلقًا.
- عند أول دخول من Google، يعيد النظام استخدام مسار onboarding نفسه: حالة سحابية فارغة واختيار صريح للبداية أو استيراد الضيف. الحساب العائد يحمّل صفه مع revision/RLS المعتادين. لا يتم نسخ بيانات المؤلف أو استيراد الضيف تلقائيًا.
- ربط البريد والهويات يظل من اختصاص Supabase Auth. لا ندمج مستخدمين بناءً على مقارنة البريد داخل التطبيق ولا ننقل حالة المستخدم يدويًا.
- الإعداد التفصيلي وURI الإرجاع وقائمة تحقق الدخول الحقيقي في `docs/SUPABASE_SETUP.md`. لا تتوفر أدوات لإدارة Google Cloud أو أسرار OAuth؛ تحققنا فقط من أن Supabase يعلن المزود وأن Preview يبدأ التفويض بنجاح. Production لم يتغير.

## اختبارات قبول إلزامية

- إنشاء حساب A ثم تأكيده ثم تسجيل الدخول، ومن جهاز آخر قراءة خطته بعد إعادة التحميل.
- حساب B لا يستطيع قراءة أو تعديل حالة A، حتى بإضافة `user_id` في Body أو query.
- ضيف لم يوافق على رفع بياناته؛ تسجيل الدخول لا ينسخها؛ استيراد صريح يحفظها في حساب A فقط.
- خروج A يحجب بياناته ويعيد بيانات الضيف المحلية الأصلية؛ دخول B لا يعرض أي بيانات لـA.
- تضارب تعديل جهازين يعرض رسالة ويوقف الكتابة بدلاً من آخر كتابة تمحو الأولى.
- كلمة مرور خاطئة، OTP منتهي، استعادة كلمة مرور، مهلة الجلسة، وانقطاع الشبكة: حالات مفهومة بلا خسارة صامتة.
- إنشاء الحساب يرفض كلمة مرور تأكيد غير مطابقة قبل إرسال الطلب.
- حساب جديد يخفي حالة الضيف أثناء الإعداد، وإغلاق الإعداد يعيد الضيف دون حفظ بيانات الحساب فوقه.
- Google OAuth: حالة مفقودة/مختلفة، verifier مفقود/غير مطابق، إلغاء/خطأ من المزود، رفض code replay، كوكيز جلسة محمية، وتجديد وخروج.
- OAuth حي بحسابي Google اختباريين: onboarding جديد، استعادة رحلة عائدة، عزل/تبديل الحساب، وعدم استيراد guest تلقائيًا؛ لا يُعد mock إثباتًا لعمل Google الحقيقي.
- اليوم والخطة والمصحف والتسميع والإحصائيات لا تتعطل ولا يظهر AI.
